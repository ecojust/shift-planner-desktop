# 内置 CP-SAT 本地排班求解器

使用固定版本 `ortools==9.14.6206`，纯本地 stdin/stdout 单次 JSON 协议，无 HTTP 服务、数据库或网络请求。开发模式直接使用项目 `solver/.venv` 的 Python；发行版把 Python 和 OR-Tools 冻结为完整 `onedir` 资源目录，在 Tauri 安装包中随应用分发，最终用户不需要单独安装 Python。

跨平台开发与验证，在项目根目录执行：

```sh
npm run solver:ensure -- --dev
npm run solver:test
npm run desktop:dev
```

`solver:ensure -- --dev` 按需准备虚拟环境并验证引擎信息和小型求解，不执行 PyInstaller；已有同架构的正常环境会复用。`desktop:dev` 的 npm 前置钩子会自动执行这一检查。macOS/Linux 也可直接运行 `solver/.venv/bin/python solver/main.py --info` 或 `--self-test`；Windows 对应解释器为 `solver/.venv/Scripts/python.exe`。

`--info` 实际加载本地原生引擎后返回 OR-Tools 版本。`--self-test` 进一步执行一个小型、双工作线程 CP-SAT 模型并检查最优解；不读取用户的排班数据。

发行构建执行 `npm run solver:build`，使用 PyInstaller `--onedir` 收集完整运行时到 `src-tauri/solver-runtime/`。Tauri 通过资源映射包含整个目录，运行时从应用 `resource_dir()/solver-runtime/shiftflow-solver`（Windows 加 `.exe`）启动；不再采用 `externalBin` 的平台后缀单文件，也不需要启动时解压 onefile。目录中的关联库必须一并分发。开发模式始终调用项目固定虚拟环境和 `main.py`，不从界面接受解释器或脚本路径。

运行 `npm run solver:doctor` 可离线对比源码环境与发行运行目录的 `--info`、`--self-test`，报告写入 `solver/build/diagnostics-latest.json`。它只使用内置测试模型，不读写或上传员工数据；发行目录尚未生成时，应按诊断中的缺失提示区分，不把开发 Python 正常等同于发行包已经验证。

桌面宿主使用 `--hosted`，求解器仅在 stderr 上写独立的 ASCII 阶段行：`SHIFTFLOW_STAGE_V1:loading`、`reading`、`solving`、`finishing`。分别表示进入 Python 后加载依赖、读取请求、开始约束计算和结果已写出。stdout 保持单个 JSON 响应；普通 CLI 调用不输出这些阶段行。

求解过程中，每找到一个新的可行排班，`--hosted` 还会立即在 stderr 写出 `SHIFTFLOW_SOLUTIONS_V1:N`。数量按目标月份的排班变量跨优化阶段去重；仅月外临时预排不同，仍算同一种本月方案。不包含诊断子模型或自检的解，也不表示已枚举所有可能方案。宿主将其转为当前任务的 `solver-progress` 事件，弹窗实时显示数量；数量更新不会重置计算时限，最终仍只返回一个优选排班。

桌面启动预算与计算预算独立：启动、加载和读取阶段最多 120 秒，进入 `solving` 后才开始计算看门狗（用户设置的搜索时限加 15 秒返回余量），结果阶段另留 5 秒退出余量。CP-SAT 自身仍遵守用户的原始时限。`--info` 不执行排班计算，只使用启动预算。启动失败、原生计算未响应和 CP-SAT 返回 `UNKNOWN` 是不同情况，不能统一解释为排班无解。

Tauri 为每个任务创建独立缓存子目录作为工作与临时目录；任务结束或取消后，先回收整个进程树，再尝试清理该任务目录。新版发行目录不再执行每次启动的 onefile 解压，目录管理仍用于隔离运行期间的临时文件。

## 请求与结果

stdin 读取到 EOF 后处理一份 JSON（上限 8 MiB），stdout 只写一行 JSON。标准错误可用于诊断。

```json
{
  "protocolVersion": 1,
  "requestId": "uuid-from-client",
  "state": "完整 PlannerState 对象（src/domain.ts）",
  "options": { "timeLimitSeconds": 15, "allowPartial": false, "seed": 1010, "referenceDate": "2026-10-15" }
}
```

`options.referenceDate` 为 `YYYY-MM-DD`，用于区分月外未知日期属于过去还是今天及未来。应用在请求创建时固定该日期，导出的请求可以按相同条件复现；直接调用 Python 且省略时使用系统当天日期。目标月份即使在过去，仍按用户要求生成；这一日期判断只限制月外临时预排。

结果字段：`protocolVersion`、`requestId`、`engine: "ortools-cp-sat"`、`status`、`issues`、`stats`、`message`。**只有 OPTIMAL / FEASIBLE 包含 assignments**，错误、无解和未找到结果时不能覆盖前端原排班。成功结果另外包含：

- `assignments`：本月生成结果，加上原样保留的本月锁定记录和全部月外记录。不会将月外临时预排混入这里。
- `boundaryPreview: Assignment[]`：仅为证明跨月衔接可行而生成的月外临时工作记录，`locked` 为 `false`；可预排日期中未列出的成员格子表示此次临时方案休息。应用不将其自动写入相邻月份。
- `boundaryContext`：`{ startDate, endDate, referenceDate, incompleteHistory }`。范围从本月第一周周一到最后一周周日；每项缺失历史为 `{ employeeId, weekStart, unknownDates: string[] }`。

前端根据原请求、已有记录和已生成范围，以及固定参考日期独立重建边界，校验 `assignments + boundaryPreview`；不能仅凭求解器返回的 `boundaryContext` 宣称约束成立。

- `OPTIMAL`：对当前目标已证明最优。
- `FEASIBLE`：找到满足硬约束的方案，尚未证明最终目标最优。
- `INFEASIBLE`：固定排班有明确冲突，或 CP-SAT 已证明模型无解。
- `UNKNOWN`：达到时限，尚无可行结果；不等于无解。
- `MODEL_INVALID`：请求不合法或模型验证失败。
- `ERROR`：求解器异常。

`stats` 包含实际建模加求解耗时 `wallTimeSeconds`、`shortageCount`（仅本月缺少的班次人次）、`solutionCount`（本次找到的不同本月可行排班数量）、`optimal`，以及适用时的 `objectiveValue` 和 `bestBound`。不同员工、班次、权重配置的目标值不能横向作质量百分比分数。

## 跨月范围与已有排班

计算范围扩展到完整自然周，两侧最多各多六天。例如生成 2026 年 11 月时，模型范围为 10 月 26 日至 12 月 6 日。上月、下月是否已排班，按成员和日期区分，不能由任意一条上月记录推断整个团队、整个月都已完成排班。

`state.scheduleCoverage` 可省略，格式如下：

```json
{
  "2026-10": { "employeeIds": ["employee-1", "employee-2"] },
  "2026-12": { "employeeIds": ["employee-1"] }
}
```

应用仅在成功生成并保存后自动写入 `scheduleCoverage`。每个月列出的成员已完成整月排班：有记录时使用记录，没有工作记录的空白表示排班产生的休息，无需用户手动确认。未列出的成员不继承他人的已生成范围。单独一条工作或 `off` 记录只表示该成员当天已有安排；旧备份没有此元数据时，稀疏空白保持未知，不能推断整月已排。月份、成员 ID、类型及重复成员均须通过校验。

主动请假通过成员的 `unavailableDates` 独立输入，是求解前的不可排日期；排班生成的休息不会自动写入或增加请假。生成结果与相邻月临时预排都必须遵守这些请假日期。

| 日期状态 | 本次处理 |
| --- | --- |
| 目标月未锁定 | 可重新生成，包括历史月份；目标月原有生成范围不妨碍重排 |
| 目标月锁定，或月外已有记录 | 固定保留，月外记录不要求 `locked: true` |
| 月外该成员已生成月份的空白格 | 固定为休息，不生成临时工作 |
| 月外未知，日期不早于 `referenceDate` | 建立临时变量，按完整周规则共同求解 |
| 月外未知，日期早于 `referenceDate` | 不补排、不虚构休息；发出历史不完整警告 |

过去缺失历史按成员分别处理。该成员在一周可计算 `d` 天时，最低要求为 `ceil(ceil(周最低小时 × 60) × d / 7)` 分钟；已经明确的工作分钟和临时预排分钟共同满足它。完整可计算的七天使用完整周最低。成功结果中的 `history-incomplete` 警告明确说明这一周尚未通过完整周校验，未知部分可能影响工时、休息、连续工作和星期人数。排班休息和主动请假都不会自动减少最低要求。

例如周最低 40 小时，本月占该周四天，另外三天均为过去且未知，则要求至少 1,372 分钟，并保留历史不完整警告。如果那三天全部已有明确记录或该成员所在月已完整生成，整周须达到 2,400 分钟；如果已知月外工作已达到 2,400 分钟，本月不再重复补一份最低。未来未知的日期通过临时预排补齐，不能只按本月片段折算后忽略相邻月是否可接续。

## 硬约束

1. 员工每天最多一个班次；锁定的休息或月外已有休息占据整格。
2. 班次资格和整日请假。前一天开始、跨入请假日的夜班同样禁止，未来临时预排也检查请假。
3. `staffingMode` 为 `minimum`（省略时默认）时人数 ≥ `required`，允许增排，0 也可安排；`fixed` 时人数 = `required`，不能增排，0 表示不能安排该班。该规则适用于目标月和范围内**所有今天及未来日期**，包括相邻月已有安排的日期。相邻月份已有安排无法满足人数时，明确报出日期与冲突，不自动改写。过去月外记录不追溯当前的每日人数要求。
4. 月内锁定记录和全部月外记录原样保留。模型范围内固定安排违反规则时明确报错；远离本次范围的旧错误不会阻断本月。范围之外的相关记录仍用于班间休息、连续工作和周日跨夜尾段的周上限检查。
5. 按周一至周日累计实际工作分钟。周日夜班拆入两个自然周；同一自然周跨月的工作完整累计，跨月午夜不丢失、不重复记账。最后一个周日夜班进入下一周的分钟，仍与该下一周已知工作共同检查上限。
6. 班间最短休息包括相关月外记录。候选班次先排除与固定工作冲突的项，候选之间用包含休息时长的可选时间区间 `NoOverlap` 约束。
7. 连续工作按班次开始日期计数，本月、相关月外固定记录与临时预排一起限制。
8. 指定互斥组在同一天同一班次最多一人，可作用于全部或指定班次，包含临时预排。
9. 周最低与最高工时均为硬约束；最低只对未知过去日期采用上述明确折算，已知完整周和未来可预排周使用完整要求。月工时仅用于实际统计与工作量均衡，不设月最低。
10. 指定班次可禁止同一成员连续两天上班；周班次次数上限按周一至周日的班次**开始日期**计数，不因跨夜拆成两次，也不因月份截断而折算。
11. 星期权重约束团队总班次数及组内均摊，具体见下节；月外已有记录与临时预排一并参与。未知过去日期不能冒充零人出勤。

显式 `allowPartial: true` 仅允许每日人数不足，固定人数上限、资格、请假、周工时、休息、连续工作、互斥、班次次数和星期权重仍为硬约束。本月缺员用 `coverage` 警告和 `stats.shortageCount` 报告；月外未来缺员用 `boundary-coverage` 警告单独报告，不并入本月缺员统计。

工时统一用整数分钟：周最高向下取整，最短休息与周最低向上取整；缺失历史折算在取整后的完整周最低上进行，再向上取整。

协议员工字段 `minHoursPerWeek` 为 0–168 小时，周最低不得超过周最高（也检查取整后的分钟上下界）。旧请求缺失周最低时按 0 处理，显式 `null`、非有限数字或范围错误仍拒绝。`minHoursPerMonth` 和 `monthlyReferenceHours` 已弃用，旧请求中的这些字段会忽略，不参与验证、约束或诊断；应用的新请求不会再提交它们。

最低人数班的下限不能用于推算员工可排工时上限；固定人数班则必须保留实际容量。若员工受请假、班次资格、锁定安排等限制，即使在最低人数班增加人员也无法满足最低工时，才返回对应的 `INFEASIBLE` 原因，不返回替代排班。个人可安排量诊断使用候选班次的保守上界；若固定容量、星期比例或其他组合约束导致无解，仍由 CP-SAT 证明后报告。`allowPartial` 只放松适用的最低覆盖缺口，不放松固定人数上限或任何最低工时。

## 星期权重

`rules.weekdayWeights` 可省略，表示不约束星期比例；设置格式为 `{ "days": [6, 7], "percent": 50 }`，其中 1 是周一、7 是周日，星期不得重复或为空，百分比为 0–100 的整数。选择全部七天只允许 100%。旧 `balanceWeekends` 字段允许随旧请求传入，但已经停用，不影响约束或公平目标。

例如完整周实际安排 14 班次，选择周一、周二合计占 20%，两天合计安排 `ceil(14 × 20%) = 3` 班次，可分配为 1、2；其余五天安排 11 班次，各日为 2 或 3。如果该分布不满足每天每班最低人数，只能在最低人数班增排并重新计算比例，固定人数班不能超过上限。不能对每个班次类型分别取整，否则可能错误地增加团队配额。

完整可计算的周使用实际团队总班次数 `N`，包含两侧已有工作和临时预排。相邻月份已有安排固定，未来未知日期可共同选择；本月只保存目标月份的生成结果。过去记录不追溯当前每日人数，但会参与完整周的比例与均摊。未来日期始终检查当前每日人数要求，无法兼容已有安排时明确返回冲突。

如果某个过去日期仍有成员的排班未知，就不能确定当天团队总人数，因此整个日期从星期配额计算中排除；该日个别成员已有的工作仍参与个人工时等约束。只对所有成员均可核对的日期保留所属星期组的份额，不把未知日期当作零人，也不将其份额重新分给其他日期。

部分可计算周的完整周参考总数为 `N`，选中 `k` 天、占比 `p`，完整组份额为 `S = ceil(N × p / 100)`、`O = N - S`。可核对日期中包含所选组 `a` 天、其余组 `b` 天，分别要求 `ceil(S × a / k)` 和 `ceil(O × b / (7-k))` 班次；全选七天时其余份额为 0。两组内部各日仍相差最多一人。`N` 在 `0–7 × 员工数` 中取能解释已知日期的整数参考值；这只能验证可核对部分，结果仍带历史不完整警告。

例如完整周参考 35 班，周一、周六合计 40%，两天份额为 14，其余五天为 21。如果周一的过去记录未知、其余六天均可核对，则周六保留 7，其余五天保留 21；若周二也未知，其余四天保留 `ceil(21 × 4 / 5) = 17`。该折算只用于缺失过去历史；未来未知日期会建立实际临时变量，按整周人数计算。

星期配额按班次开始日期计数，跨夜不拆成两班；工作小时仍按实际分钟拆分。没有额外的逐班周总量配额，每日人数模式、个人规则、单独配置的周班次次数限制和星期权重共同约束结果。

启用星期权重后，两个星期组份额和组内均摊仍是硬约束。默认严格模式要求每天各班符合最低或固定人数；显式 `allowPartial` 仅允许每日覆盖缺口，不减免固定人数上限、星期份额、组内均摊或工时要求。已证明与其他规则冲突时返回无解，限时没找到方案则返回 `UNKNOWN`。人员每日最多一班、资格与请假限制始终生效。

## 优化目标

采用约束求解，不使用遗传算法，也不把违反硬规则当作可交易的罚分。

按优先级依次优化：允许缺员时先最小化本月缺员，再最小化月外临时衔接缺员；随后最小化本月和临时预排的总安排次数，最后改善本月公平性。不能为了多安排一个月外临时班次而牺牲本月覆盖，也不会只为提高公平分数无限增排。**只有上一阶段最优值已被证明，才锁定该值并进入下一阶段**。某阶段仅得到可行方案时，会明确返回 `FEASIBLE` 而不宣称最优；后续优化未完成时保留已取得的可行排班。所有阶段共用用户设置的总时间预算。

公平性是以下整数指标的加权和：

- **工时公平**：员工实际落在本月的工时 / 每周工时上限 × 1000 后取整，最大与最小负荷之差 × 10。
- **班次轮换**：各班次可排员工本月次数的最大值与最小值之差，各 × 200。

完全无法参加某项排班的人不纳入该项公平比较。公平性是偏好，不改变请假、人员互斥、工时和星期权重等硬限制。原周末公平目标已移除。固定班次津贴不计入求解目标，由前端按最终排班的开始日期独立汇总。

## 规模与时间保护

最多 200 人、24 班次、目标月 31 天、扩周范围最多 42 天、15 万候选变量（规模预算包含扩展日期）；排班历史 2 万条，同班互斥约束系数预算 200 万。日期范围 1900–2200 年；最短休息 0–168 小时、连续工作上限 1–366 天，周工时不超过 168 小时。默认总建模求解预算 15 秒，可设 0.01–60 秒；采用 2 个求解工作线程。模型达到时限会返回 UNKNOWN 或已有 FEASIBLE，不能承诺大规模复杂模型在时限内必有结果。

测试把 Python 的本月结果和 `boundaryPreview` 一起交给 TypeScript `validateBoundaryPreview` 独立交叉检查，并以独立时间枚举核对完整自然周实际分钟。覆盖两侧已排/未排、成员已生成范围不同、稀疏历史与明确休息、未知过去告警、未来双侧预排、跨年跨夜、请假互斥、周班次次数、星期权重、最后周日尾段、远历史隔离、分钟取整和允许缺员仍不放宽硬规则；另验证只有月外预排不同不会增加本月方案计数。
