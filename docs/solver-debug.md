# 导入、导出排班规则与复现求解

在「排班日历」点击「导出规则」，可将当前月份的成员、可上班次、请假、班次人数模式、工时与排班规则导出为一个 JSON 文件。文件也包含锁定安排、上下月排班记录与成员月份完整性，以复现月首尾自然周的工时、休息和连续工作约束。

排班失败后可用「导出本次规则」保存那次求解的输入；它保留原来的随机种子、时限和人数要求，即使随后修改了界面设置也不受影响。日历工具栏的「导出规则」始终导出当前设置。

## 在应用中导回规则

点击排班日历「导出规则」旁的「导入规则」，选择之前通过「导出规则」或「导出本次规则」保存的 JSON。应用会预览团队、月份、成员与班次数量，以及所有月份的排班和锁定记录数量；点击「确认导入」后替换当前工作空间。

导入恢复文件中的成员、班次、完整排班规则、所有月份的排班（含锁定安排）、日期类型和津贴设置。文件缺少的日期类型或津贴设置使用默认值。导入后不会自动排班，可先查看排班检查结果，再按需重新生成。

规则导出不含头像；导入时，成员 ID 与姓名都相同的本机头像会保留。有变化的配置字段会记录为「手动修改」及本次导入时间。文件中的 `debug.originalHourDefaults` 会恢复原来的周最低工时；没有这份元数据时，保留文件里的周工时设置。旧月最低及月参考字段统一忽略，导入后不会重新启用。

自动排班等待时长仅恢复界面支持的 5、15、30、60 秒。导入不会复用文件中的随机种子 `seed` 或 `allowPartial`，这些选项仍可用于下方的求解器复现。

此入口接受带有 `protocolVersion: 1` 和 `state` 的规则导出包，文件上限为 8 MiB。格式错误、无效数据或成员／班次引用不一致时会拒绝导入。应用先完成校验和保存，再替换当前数据；保存失败时保留原工作空间。包含头像的完整备份仍通过「备份与恢复」导入。

## 在源码求解器中直接运行

首次使用先按项目说明安装本地求解器依赖：

```sh
npm run solver:setup
```

macOS / Linux，在项目根目录运行（文件名有空格时保留引号）：

```sh
solver/.venv/bin/python solver/main.py --input "/路径/排班规则.json" > result.json
```

Windows PowerShell：

```powershell
solver\.venv\Scripts\python.exe solver/main.py --input "C:\路径\排班规则.json" > result.json
```

也可将 `--input` 和文件路径作为调试器的程序参数，入口为 `solver/main.py`。该方式从文件直接读取，不需要在终端输入 EOF。已打包的求解器也支持相同的 `--input` 参数。原有标准输入协议保持可用。

## JSON 内容

- 根字段 `protocolVersion`、`requestId`、`state`、`options` 是求解器可直接接受的完整请求，无需拆包或转换。
- `state.employees` 保留周最低和最高工时；同时保留班次、规则、月份、排班历史与 `scheduleCoverage` 完整性记录。已弃用的月最低及月参考字段不会进入求解请求。成员头像不影响排班，因此不放入求解请求和调试文件；完整应用备份仍包含头像。
- `options` 保存 `timeLimitSeconds`、`allowPartial`、`seed` 和冻结的本机日期 `referenceDate`（`YYYY-MM-DD`）。该日期决定缺失的月外日期属于未知过去还是未来预排；复现时应保留，避免换一天运行改变问题含义。应用始终发送 `allowPartial: false`，严格满足班次人数要求；底层协议保留此字段供历史请求复现，界面不提供缺编模式。
- 额外的 `debug` 字段记录导出时间、构建版本、来源和运行环境；如提供了原始设置，还记录原始周最低工时值。求解器忽略这个辅助字段。

该文件包含员工姓名和请假等排班数据，向他人发送前可按需匿名化姓名。不要删除仍会影响约束的日期、班次资格、上下月安排或 `scheduleCoverage`；匿名化成员 ID 时也要同步修改排班引用和生成范围中的 `employeeIds`。

`result.json` 中只有 `OPTIMAL` / `FEASIBLE` 会包含可用的 `assignments`。`INFEASIBLE` 表示已证明规则冲突；`UNKNOWN` 表示限时内尚未找到方案，不等于无解。同一输入便于复现约束与诊断；多线程搜索的耗时、优化结果和具体排班不保证逐次完全一致。

规则 JSON 可通过「导入规则」恢复，也可直接用于求解器调试；包含头像的完整迁移使用原有备份功能。

## 双向跨月自然周

月初与上月末、月末与下月初都按完整周一至周日处理。已有相邻月记录固定保留，包括未锁定记录；成员的 `scheduleCoverage` 表明对应月份已完成生成，空白是排班结果中的休息。它不表示主动请假，也不会修改 `unavailableDates`；请假独立限制可排日期。旧文件缺少完整性记录时，不从一条工作或休息记录推断其他日期已知。

相对于 `options.referenceDate`，未知的今天与未来日期由求解器临时试排；未知的过去日期不会补造，也不按休息计算。没有未知过去时，周最低、最高及星期权重按完整自然周求解；过去历史不完整时，最低按可核对天数折算，权重仅保留可核对星期份额，同时返回警告，整周仍待核对。未来预排并不保证相邻整月可排。

`result.json` 的 `assignments` 用于正式的目标月结果与原有固定记录。可选 `boundaryPreview: Assignment[]` 是月外未来工作班次；其中没有工作记录的未来空白只代表本次临时休息，不自动保存。`boundaryContext` 包含 `startDate`、`endDate`、`referenceDate` 及 `incompleteHistory: [{ employeeId, weekStart, unknownDates }]`，用于解释未完成的历史核对。不要把预排数组直接混入正式排班或当作相邻月已完整生成。

应用独立检查预排的日期、资格与规则后，只保存目标月并自动记录该月当前成员已完成生成；其他月份已有记录不变。之后排相邻月份时，前一次已保存记录成为固定上下文；冲突需调整对应月份或规则，不会自动联排覆盖。

为复现此类问题，必须保留冻结的参考日期、自然周相关的上下月安排，以及每个成员的完整性范围。跨夜工时按实际分钟所属周计算，不重复抵扣。完整口径与例子见[成员工时](HOURS.md)。

## 班次不相连与周班次限制

这两类规则由「排班规则」面板逐条管理，保存后包含在备份、规则 JSON 和 Excel 的「班次说明」中。例如：

```json
{
  "nonConsecutiveShifts": [{ "id": "night_gap", "shiftId": "night" }],
  "weeklyShiftLimits": [{ "id": "night_cap", "shiftId": "night", "maxPerWeek": 2 }]
}
```

以上字段位于 `state.rules`，班次 ID 必须对应 `state.shifts` 中的班次。例子表示每人不能连续两天上夜班，且每周最多上两次夜班。

- 两类规则都对每位成员单独生效，各可配置最多 24 条，同一类中每个班次只能出现一次；同一班次可同时使用两种限制。
- 不相连检查开始日期相邻的两天，至少一天须在当前月份。上月最后一天和下月第一天的已知安排也会参与检查。
- 周次数按周一至周日的班次开始日期统计，包含所有与当前月份相交的自然周。月初、月末不足整周时不折算上限；该周已知的跨月安排即使未锁定也计入。周日跨夜至周一只计在周日所在周。
- 次数上限为 0–7 的整数；0 表示不安排该班次。不配置表示没有额外限制，旧备份无需补字段。
- 不追溯与当前月份无关的历史日期或自然周；本月未锁定安排可以重新分配。
- 这些是硬规则。冲突类型为 `consecutive-shift` 或 `weekly-shift-limit`，诊断会提供成员、日期、班次及可调整的方向。
